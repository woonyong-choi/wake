# 첫 실행·설정·연결 관리 흐름

첫 실행은 이전 실제 기능을 복구해 공통 정의로 유지한다. 이 파일은 기능 흐름을 소유하며 설정의 경계선·반경·행 모양은 design/screens 소유다.

공통: [권한·대상·7상태·왕복·원본 대조·표시](../product.md#공통-계약-적용). 현재는 소스 확인, 시험·캡처·실제 연결 합격은 별도다.

## FLOW-ONB-001: 첫 실행의 단계와 재진입

- 목표: 입력: kit.firstRun.done이 없는 격리 설정으로 앱을 열고 클러스터 연결을 실패시킨 뒤 뒤로·다음·재시작한다 → 기대: firstRun은 clusters → ai → setup 세 단계다(D-USR-2026-11-18-20). clusters는 시작 화면 없이 실제 context 열거와 진행·실패 원인을, 없으면 그 자리의 연결 방법을, ai는 공급자 연결("AI 없이 계속")을, setup은 실제 성공 결과 요약과 AI 권한 기본값(읽기만)·언어·테마를 보여 주고 "시작"은 연결된 클러스터 홈으로 간다. 예전 단계(welcome·permission·done)에서 멈춘 첫 실행은 그것을 넘겨받은 단계로 이어진다. 필수 계정 가입이나 가짜 클러스터·숫자 채우기를 두지 않는다. 도구·Git·agent 연결은 같은 설정 정의로 접근할 수 있어야 하며 연결하지 않은 것을 완료로 표시하지 않는다. 다시 보기에서는 kit.firstRun.done 상태에 따라 같은 첫 실행 단계를 연다. → 실패: 단계가 빠지거나 연결 실패·미설정 agent가 done에서 완료로 보이면 실패.
- 추가 조건: 입력 각 대상 화면에 실제 이어갈 작업이 있는 경우와 없는 경우 입력 → 기대 컨트롤마다 가능한 실제 행동을 제공하고 진행 로그는 실제 작업에서만 발생 → 실패 아무 일도 하지 않는 등록 핸들러나 가짜 진행 로그가 노출. 공통 판정은 [SCR-SETTING-STATE](../screens/settings.md#SCR-SETTING-STATE)에 연결한다.
- 추가 조건: 온보딩과 설정의 클러스터/도구 연결 화면을 동일 상태·폭·테마의 승인 견본과 대조 → 기능·상태를 보존하며 역할별 계산 스타일과 부품 인자가 일치 → 기능은 정상이어도 미승인 스타일/픽셀 차이가 남으면 실패. 공통 판정은 [Q-008](../quality.md#Q-008)에 연결한다.
- 현재: `apps/wake/app.config.js`의 firstRun은 세 단계(clusters·ai·setup, aliases로 예전 단계 이어 하기)이고 언어·테마·AI 권한 기본값은 setup.options에 둔다.
- 차이: 없음([첫 실행 단순화와 시작 화면 삭제](../tasks.md#first-run-simplify)).
- 고정 장치: `kit/shell/first-run.test.mjs`의 단계 복원·세션·취소·늦은 발견 시험, `apps/wake/app.config.test.mjs`의 세 단계·완료 이동·집계 시험. 실제 첫 실행·실패·재시도 결과는 [H-006 실행 판정](../tasks.md#H-006-run)이다. 표시 선호는 마지막 단계에 둔다(D-USR-2026-11-18-20).
- 출처: D00078 D00445 D00972 D00973 D00974 D00994 D01003; R-010,R-058,R-059; 1차; 1차

## FLOW-ONB-002: 설정에서 같은 연결 흐름

- 목표: 입력: 첫 실행과 설정에서 동일 CLUSTER_ADD 항목을 고르고 연결 성공 후 본문에서 설정으로 돌아와 해제한다 → 기대: 첫 실행과 설정은 같은 CLUSTER_ADD/CLOUDS/connectPages를 쓴다. 연결 목록에서 현재 cluster를 고르고 기본 namespace·읽기 권한·도구·GitOps·agent를 확인한다. 홈 칩은 본문 상태 화면으로, 연결 추가·인증·해제는 설정으로 간다. 설정을 열기만 해도 연결 상태를 변경하는 동작은 없어야 한다. 연결한 행은 확인과 해제, 대기 중인 행은 취소, 실패한 행은 재시도를 제공한다. → 실패: 두 진입점의 입력·단계·오류가 다르거나 설정을 열기만 해도 연결 설정이 바뀌면 실패
- 현재: `apps/wake/app.config.js:234`는 CLUSTER_ADD/CLOUDS로 connectPages를 만들고 `apps/wake/settings-pages.js:51`이 이를 설정 행에 사용한다.
- 차이: AI 연결 설정은 `ai-connect.js:22`에서 렌더 중 aiserver.set을 호출해 설정을 열기만 해도 서버 상태를 바꾼다. → TASK-A3-ONB-002
- 고정 장치: `apps/wake/data/connect-flow.test.mjs`, 시험 `같은 뜻의 단계는 같은 이름: 모든 방법·다시 확인의 단계가 공용 단계 표에 있음`. 실제 설정의 동일 context 접속 실패·재시도와 UID 회복은 [H-006 실행 판정](../tasks.md#H-006-run)이다.

## FLOW-SET-001: 장애 알림을 실제로 켜고 끄기

- 목표: 입력: wake.notify.incidents를 켠 뒤 같은 incident 상태 전이를 두 번 수신하고 끈 상태에서 새 전이를 수신한다 → 기대: 사용자가 장애 알림을 켜면 실제 incident/alert 변화에 대한 알림을 전달하고 끄면 새 알림을 발송하지 않는다. 감지·저장·사건 목록은 스위치와 독립이다. 중복 수집·재시작·재시도로 같은 알림을 반복하지 않는다. (기본값 채택, 번복 가능) OPEN-PF-011: incident ID+상태 전이 ID+repeat 회차+채널을 전달 중복 키로 삼고 재발 전이는 새 알림으로 전달한다. 다시 켤 때 과거 알림을 일괄 재전송하지 않는다. 운영체제 권한 거절과 전달 실패를 성공으로 표시하지 않는다. 알림을 누르면 같은 incident로 간다. 비활성 행을 삭제하는 것으로 이 요구를 종료하지 않는다. → 실패: 켜짐에서 알림이 없거나 중복 전송되거나 꺼짐에서 새 알림이 발송되면 실패
- 현재: `apps/wake/app.config.js:259`의 notify-incidents 스위치는 disabled:true다.
- 차이: 스위치를 켤 수 없고 incident 상태 전이와 실제 알림 발송을 연결하는 동작도 없다. → TASK-A3-SET-001
- 고정 장치: 고정 없음 → TASK-A3-SET-001
- 출처: D-USR-2026-11-16-7; D00993; R-049,R-058; U00697 사용자 선택; 1차 T2.

## FLOW-SET-002: namespace 표시 설정

- 목표: 입력: cluster c1과 c2에 같은 namespace n1이 있을 때 wake.ns.show.c1.n1을 끄고 재시작한다 → 기대: namespace 표시 스위치는 cluster별로 저장하고 재시작 뒤 유지한다. (기본값 채택, 번복 가능) OPEN-PF-010: 숨김 범위는 namespace 선택기·검색·리소스 목록이며 이미 열린 상세·인시던트 근거에는 적용하지 않는다. 이는 표시 선호이며 RBAC 권한이나 수집·원본을 바꾸지 않는다. 이미 열린 숨김 namespace의 대상을 다른 namespace로 조용히 교체하지 않는다. 선택 항목 없음과 원본 읽기 실패는 구별한다. 적용 화면 목록은 T2에서 값·화면 계약과 함께 고정하고 현재 미적용 행을 완료로 부르지 않는다. → 실패: c2의 n1까지 숨거나 이미 열린 c1/n1 상세 대상이 교체되거나 RBAC가 바뀌면 실패
- 현재: `apps/wake/settings-pages.js:201`의 namespace 표시 스위치는 disabled:true다.
- 차이: cluster별 숨김 선택·재시작 유지·검색과 목록 반영을 조작할 수 없다. → TASK-A3-SET-002
- 고정 장치: 고정 없음 → TASK-A3-SET-002
